# Patterns by module category (start from the matching template)

| Idea | Kind | Notes |
|---|---|---|
| Change system properties | props | system.prop + props.list check after boot |
| One-time tweak (sysfs/proc write, setting) | basic | write, then dbg_check the value read back |
| Background watcher/loop | service | lock dir, pid check, validated config, sleep interval 10-3600 s |
| File replacement/overlay | basic | files under `system/`; verify with `ls`/`cmp` check |
| Learn what the device supports | canary | read-only probes, upload log |
| Zygisk/native hooks | (not templated) | needs a native build; ask first, test only with a rescue path |

General rules
- Always read a value back after writing it and log a CHECK.
- Config is data: parse `key=value` with grep/cut, never `source` a user-editable file.
- Validate numbers (`case ... *[!0-9]*`), clamp ranges, quote variables.
- Prefer `service.sh`. In post-fs-data do only what must precede mounting.
- Use `BT_ONCE=1` to run a loop template once in simulation.
- Bootloop avoidance: settle after boot before heavy work, stagger light and heavy cycles, cap every file you grow, one untested module per reboot. See bootloop.md.
- Thermal zones are not all temperatures (T3, 2026-11-25): on the test device some `thermal_zone*/temp` values are levels, steps or voltages (observed `soc`=274, `vbat`=4085 mV, negative step values). Convert millidegrees, then keep only plausible temperatures (about 0–120 °C) and drop zone types ending in `-lvl*`, `-step`, `-bcl*`, `-vph*`, `-ibat*`, `-vbat*` before taking a max or charting.
- `wm size` / `wm density` can fail from a module service (T3: "Failure calling service window"). Use `dumpsys display` (filtered) or the density prop instead.
- `/proc/cpuinfo` may have no Hardware/model name lines (T3 on this kernel). Identify the SoC from `ro.soc.model` / `ro.board.platform` props.
- Shell on the test device is BusyBox ash standalone: arrays=no, but `[[ ]]`, `${x//}`, `local`, arithmetic, printf and case all work (T3). Templates still stay POSIX so they run everywhere.
- Hot install / live apply (research 2026-11-25): KernelSU-family managers support official hot install — a module declares `MODULE_HOT_INSTALL_REQUEST=true` and optionally `MODULE_HOT_RUN_SCRIPT=<script>` in customize.sh, and the manager applies it without a reboot (script runs in the global mount namespace, ~30 s budget). For a container/loader module that applies other modules live: props via `resetprop` (save old values first, restore on disable), run `service.sh`/`boot-completed.sh`/`post-mount.sh` immediately, `sepolicy.rule` live only when `magiskpolicy` exists, `system/` files only via tracked bind mounts behind an explicit config flag (default off), Zygisk/native code never hot-loads (needs a soft reboot / zygote restart). Re-apply enabled modules after every boot from the loader's own service. Guard zip extraction against path escapes (check entry names for `../` or absolute paths before unzipping). Proven on the FinaSU test device 2026-11-25 (HotMod: scan/install/list via Action log).
- Module banner (FinaSU convention, T3 2026-11-25): `banner=<file>` in module.prop pointing to an image in the module root (1280×426 px, no baked-in text, ≤ 3 MB). FinaSU renders it as the module card background in its list; a container module can copy banners into its own webroot (`banners/<id>.<ext>`, size-capped) to render banner cards. Verified on device: HotMod v2.0.0's banner shows in FinaSU's module list.
- KernelSU module repo integration (research 2026-11-25): modules.kernelsu.org is a static catalog indexing immutable GitHub releases — one module ZIP per release, id/version/versionCode from the `module.prop` inside the ZIP, SHA-256 locked. Module page: `https://modules.kernelsu.org/en/modules/<id>/` with a Download link to the GitHub release asset and a Transparency section (repo, tag, SHA-256). A module can list the catalog (parse `/en/modules/<id>/` hrefs from the index page) and install from it (fetch the module page, take the first `github.com/.../releases/download/...zip` URL and the first 64-hex SHA-256, download with curl, verify the hash when present, then install). Treat page parsing as best-effort (T4) and say so in the UI; never install without the hash check when a hash is published.
- Superuser grant list is best-effort only: managers store grants in incompatible places with no shell API. Readable attempts: `sqlite3 /data/adb/magisk.db "SELECT package_name FROM policies WHERE policy=2;"` when sqlite3 exists, else `strings` on known db files (`/data/adb/ksu/*.db`, `/data/adb/magisk.db`) filtered by a package-name regex, capped (e.g. 100). Label the result approximate in the UI; an honest empty state beats a fake list. (FinaSU test device: unreadable from a module — empty state shown, 2026-11-25.)
- Browser mode for a WebUI: if `busybox --list` includes `httpd`, serve the module's own webroot on `127.0.0.1:8765` (pidfile, start/stop/status commands) so any browser on the phone can open the UI in file mode. Check the applet first and report honestly when absent; bind loopback only, never 0.0.0.0.
- Cloud sync via WebDAV (curl only, no rclone needed): one-way upload with size-skip — HEAD each remote file, compare Content-Length, MKCOL each path part, PUT missing/changed files, URL-encode spaces (%20). Count uploaded/skipped/failed into a result file (the loop runs in a pipeline subshell) and log one summary line. Credentials come from config keys (WEBDAV_URL/USER/PASS/DIR); never log them. Proven against a local server (upload + skip on second run), Sortify v9, 2026-11-25. rclone remains the alternative when installed.
- Config migration in customize.sh: on upgrade, read known keys from the previous install's config (`/data/adb/modules/<id>/<conf>`) and carry them into the new one — allowlist of keys, reject values containing `"`, `$` or backticks (the config is sourced later), escape `\&#` for sed, and convert renamed legacy keys. Print what was kept. (Sortify v6–v8 → v9.)
- WebUI settings via a CLI `set` command: the WebUI never writes config directly; it calls `sh <mod>/cli.sh set KEY "VALUE"` where the CLI allowlists keys, rejects `"`, `$`, backticks, backs up the conf first, then sed-replaces or appends `KEY="value"`. The service reads config with grep (never sources a user-editable file) so a bad edit cannot break the loop.
- Cadence tiers for speed without jank: service = settle after boot (15–60 s) → light cycle (fast `/proc`+`/sys` reads, 30–120 s) → full snapshot hourly (heavy commands, probes, devlog). WebUI = bridge poll 100–1000 ms with a speed selector, file fallback 1–2 s, paused while hidden. Instant-feeling UIs come from the bridge tier, not from making the service faster. See design.md for render budgets.
- Merging modules: keep one surviving id (flash-over upgrade), port the others' work blocks into its service tiers, keep the bootloop guard and logging untouched, and tell the user to remove the old modules so two services don't double the work. (SysDiag Local + Skill Lab → SysDiag Lab, 2026-11-25.)
